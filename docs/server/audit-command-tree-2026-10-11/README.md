# Vivi command tree against the project server — audit, 2026-10-11

Scope: all 120 leaf commands of `vivi` (18 groups), exercised in a synced
two-mailspace world against a private local `vivi-server`, using the real
binaries at vivi `main` `e1f5ead` and vivi-server `main` `a91b6b9` (debug
builds). Four read-only auditors ran in parallel, one per group. This page
is the synthesis; the four reports hold every row and repro.

Docs in the repos are stale by default, so every row was judged from running
the binary, not from prose. The headline claims below were re-checked by hand
on a fresh world (marked **verified**); the rest are the auditors' findings and
carry the repro in their report.

causes, below.

## Follow-ups (not yet scheduled)

Small items found while working through the audit, in no particular order.
None blocks use.

1. **Message-ID leaks the machine hostname.** vivi's RFC `Message-ID` is
   generated by the `mail-builder` crate as `<timestamp.rand.rand@hostname>`
   (`gethostname`), so every letter shows the author's machine name to the
   server and every project member. Set the id explicitly in
   `src/message/compose.rs` with the mailspace's `<prefix>.local` as the
   right-hand side (or disable the crate's `gethostname` feature). New letters
   only; existing letters are immutable bytes. Safe: nothing parses the
   right-hand side. Added at the owner's request, 2026-10-11.
2. **Cursor epoch (the UIDVALIDITY problem).** A server that is wiped or
   restored leaves clients with a cursor ahead of the data, and `pull` skips
   silently. Have the server return an epoch id with each list and the client
   reset its cursor when it changes. Today the binding carries a fixed
   `UIDVALIDITY` constant.
3. **Stuck-letter hint.** An oversize or foreign-From letter keeps `sync push`
   non-zero until trashed; the output should say how to clear it.
4. **Chat outbox drop verb** for a permanently rejected message
   (`chat outbox drop <id>|--rejected`); today it needs a state-file edit.
5. **`mail deliver` and `mailspace import` mint no backlog node** themselves
   (audit repair does), and chat's backlog attach passes no dependencies.
6. **A dependency not yet held does not block** a dependent until its letter
   arrives, so the dependent can be dispatched in that window.
7. **Event letters, part B** (queued after part A): verdict, repo and tip as
   headers on the report; the task-to-need parent header and rebuilding
   `need bind` from it; `promoted` events; `watch` waking on events.
8. **Recovery without raw HTTP:** a vouch command, a create-project command,
   and a server re-key path for a lost checkout key.

## What works

- The letter path itself: `mail send`, `mail reply`, `mail list/show/dump`
  with remote and local addresses, `need/task/want send`, pull filing by
  address, rename aliases (`role rename` then old and new addresses both file
  under the canonical role), and every `sync` leg the 84-leg smoke covers.
- The mailspace id guard: a config id that disagrees with its sidecar is refused
  by every command tried (28), with a two-file message ending "Nothing was
  changed", and the files and store were left untouched.
- `role add`, `role rename`, `mailspace init/description/archive export/
  identity add|list|rename`, and the 27 local-state commands that are
  correctly local (`WORKS-LOCAL`).
- Chat against the rooms API on the same server, within its own surface.

## Root causes

Ranked by how much they break a Mind loop in a multi-member project.

### R1 — The sender's own copy of remote-addressed work is a live backlog item under the role `sent` — verified

`need/task/want send --to hand@<other prefix>.local` leaves a copy in the
sender's `sent` role, minted as a backlog node. Everything downstream then
treats it as dispatchable work:

- `vivi step` dispatches it as kind `sent`; a **want is not parked** (it is
  parked on the receiving side). `graph activate` then refuses it (role `sent`).
- `need/task/want list` and `dump` cannot see it (`need list --for hand`
  prints "no needs"), so the author cannot list their own open work.
- `--depends-on <that handle>` is refused ("has role 'sent'; expected a task,
  need, or want handle"), while `graph connect` accepts it (a local-only edge).
- Closing the sent copy updates its folder but not its graph node.
- `sync prune` evicts these copies although its help says "never open work":
  the policy keys on the folder role, and the folder is `sent`. After eviction
  `step` reports `item_missing` and `graph audit --repair` repairs nothing;
  `resync` heals it. **Verified:** dry run lists `N1`, `W1`, `T4` as "sent".

Cause: `src/mailspace/delivery.rs::attach_sent_work` mints the node on the sent
copy; `src/mailspace/step.rs::adjudicate_node` derives kind from the row's
folder role instead of the node kind. Severity: blocks use.

### R2 — Work held for another mailspace's role is in this mailspace's backlog, dispatched by `step`, counted by `boot` — verified

The server shows every work item to every member (decided: need/task/want are
visible to all members). The client files a letter whose recipients are all
foreign under its raw To address, and `src/sync/filer.rs::placements` marks
that fallback `attach: true`, so the node joins the local backlog. Then:

- B's `step` offers a task that belongs to A's `hand`, B's `board` does not
  list it, `boot` counts it. **Verified** (`step` lists it, `board` count 0).
- It can be activated but not closed: `task done <h> --for hand` is "message
  not found", `--for hand@<A>.local` is "external recipient not allowed".
- `graph complete` clears it and `graph audit --repair` ("folder wins") reopens
  it.
- The governance `vouch` letter sits in every checkout's unabsorbed mail
  forever: no role can absorb it.

Both mailspaces end up dispatching every item. Severity: blocks use (duplicate
dispatch, stuck nodes). The fix is local to the filer's fallback placement and
to the readers that do not filter nodes by "does this mailspace hold the item".

### R3 — Lifecycle state is local-only and nothing machine-readable travels — verified

`done`, `reopen`, `promote`, `drop`, `bind`, `absorb`, priority and verdict
change local state only. `done --note` sends a plain `Re:` mail with no done
marker. Consequence: the sender's `step` keeps re-dispatching work the other
side closed, forever; `step --apply` answers `not_settled`; the only clear is
`graph complete`. **Verified:** after B `task done` and a sync of both sides,
A's `step` still dispatches the task. This is the known "closing a need as an
appended event" proposal; the audit shows it is not optional for a Mind loop.
Severity: surprises (re-dispatches closed work).

### R4 — Dependency edges are dropped on pull — verified

`X-Vivi-Depends-On` travels in the letter, but `src/sync/filer.rs::ingest_row`
calls `backlog_attach(kind, &handle, &subject, &[])` with no dependencies, and
`graph audit` only checks node existence, kind and state, so it reports clean.
On the receiver `graph ready` calls a dependent task ready while `task list
--blocked` calls it blocked. **Verified:** B sent a task depending on a need;
on A `blocked (none)`. Severity: blocks use for ordered work.

### R5 — Watchers never wake for synced arrivals

`mail watch`, `mailspace watch`, and `need/task/want watch` filter on event
kind; `sync pull` writes events with command "sync pull", kind `sync`, which
is filtered out, and `--kinds sync` is rejected. A hand blocked on `watch`
never sees a letter that arrived by sync. Severity: blocks use for watch-driven
loops.

### R6 — Letters that cannot be delivered are accepted, then lost or stuck silently

- A letter over 64 KiB prints "queued for sync", is skipped on every sync with
  exit 0, and `sync status` shows `unsent 0`.
- A letter whose From names another mailspace (via `mail deliver`, an import
  from a foreign mailspace, or a re-minted id) is pushed, accepted by the server
  (which never parses letters), then refused by every puller and lost. There is
  no From-prefix check at push.
- "queued for sync" is printed for a prefix nobody holds and in a mailspace that
  is not synced; the server accepts a letter to an unregistered prefix.
- `mail deliver` rejects remote To/Cc (known; `deliver_raw` uses
  `resolve_identity`, not `classify_recipient`), so there is no way to send an
  attachment to a remote address; re-delivering pulled bytes makes a duplicate.
- A refused pulled record is reported once, then the next sync is green; a
  replay (`resync`) exits non-zero by design when such letters exist.

### R7 — Unknown, retired and typo'd roles are silent

A letter for a role the receiver lacks is filed under the raw name with a
stderr-only warning, exit 0; the item is invisible on `board`/`list --for`
but present in `step` and `boot`. The sender gets no signal (a typo is a dead
letter). A `retired` role keeps receiving with no warning. `role rename`
silently adopts earlier rows filed raw under the new name.

### R8 — Recovery and concurrency gaps (sync, chat)

- No vivi command can create a project or vouch for a member; `sync join`
  tells the user to ask for a vouch the CLI cannot send. (Consistent with the
  smoke, which had to do both by raw HTTP.)
- Losing the checkout key is a dead end: the server refuses a second key for a
  name and the CLI's advice loops.
- A corrupt `sync/state.json` blocks `resync`, `fetch` and `status`.
- Two concurrent syncs on one checkout: `database is locked`, exit 1.
- One permanently rejected chat message (e.g. `--to nobody`) blocks the outbox
  of every room; `chat flush`/`send` exit 0 and there is no way to drop it.
  `chat leave` orphans outbox rows.
- A cursor ahead of the server skips silently; a project switch strands
  history; `fetch` exits 0 on a miss; `pool dispatch` can re-run a task another
  member closed.
- Chat letters do not sync as project letters (provider `vivi-room`; push skips
  them and lists them as skipped on every push; `mail reply` to them refuses).

## Findings that are not sync problems

- `memo delete` moves **any** record the identity holds to trash (a queued
  outbound need included), with no memo check; trashed work stays dispatchable
  as kind `trash`. Not sync-specific; there is no other delete verb.
- `mailspace import` between two checkouts of one project fails with a raw
  SQLite UNIQUE error, leaves an orphan row, and `--dry-run` says it would work.
- `mail thread --limit 2` returns 5. `done --note` is not idempotent.
  `want promote` before the first push travels as a need; after it is silent.
- Rules and memos never sync and their help does not say so; no rule
  evaluation engine exists.
- The server's prefix-clash remedy ("remove the id line") loops because the
  sidecar restores the id; the message must also name the sidecar.

## Decisions needed

1. **Closing as an event (R3).** Appended close letters with a machine-readable
   header, applied by the receiver and by the sender's graph. Already on the
   Proposed list; the audit makes it the main gap. It is a wire/design choice
   for the owner.
2. **Foreign work in the backlog (R2).** Recommended: hold foreign work as
   mail (`attach: false`), and filter `step`/`boot`/`graph audit` by held
   accounts. The alternative (a mind that dispatches for the whole project)
   needs an explicit "project mind" mode.
3. **Sent copies (R1).** Recommended: a sent copy of remote work is a receipt,
   not a node; dispatch and prune key on the node kind and the binding, and the
   author's lists include their own outbound work.

## Suggested order

1. R2 and R1 (filer fallback and `sent` handling): they make `step` safe in a
   multi-member project, and are small.
2. R4 (rebuild edges from `X-Vivi-Depends-On` on pull; teach `graph audit`).
3. R5 (let watch include sync arrivals).
4. R6 (refuse at send time: size, From prefix, unknown prefix; surface skipped
   letters in `sync status`).
5. R3 (needs the owner's wire decision).
6. R7, R8 and the cosmetic list.

## Method and caveats

- Harness: `audit-setup.sh WORKDIR PORT` boots a private server and two synced
  checkouts (alice and bob, roles mind and hand). The shared brief is
  `audit-brief.md`. Repros live in `repro/` and in each report.
- Local only: no staging, no network egress, no provider spend. Debug builds.
- Counts are per command; one root cause drives many rows.
- Verified by hand: R1, R2, R3, R4 and the prune claim. R5 to R8 are the
  auditors' findings with repros in their reports; not independently re-run.
- Not covered: pool kinds fly, docker, ssh and runpod; transparent mode
  (designed, not built); the rooms smoke against staging.
